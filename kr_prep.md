# Подготовка к контрольной работе

## Когда я выберу rebase, а когда merge? Почему?
rebase — для своей локальной feature-ветки, которую ещё никто не забрал: перед PR я переношу
её на свежий main и получаю линейную историю без лишних merge-коммитов.
merge — для общих опубликованных веток (main, develop): он не переписывает существующие
коммиты и честно показывает, когда ветки были объединены.

## Что произойдёт, если сделать rebase публичной ветки, с которой работают коллеги?
Rebase создаёт новые коммиты с другими хешами. У коллег останутся старые коммиты, их история
разойдётся с удалённой: при pull появятся дубли коммитов и конфликты, а push без --force
будет отклонён. Если сделать push --force, можно затереть чужую работу.

## Зачем нужен multi-remote и в каких реальных сценариях он применяется?
Несколько remote позволяют хранить один и тот же код в разных местах: зеркало/резервная копия
на другой платформе (GitHub + GitLab/Gitverse), работа с форком (origin — мой форк, upstream —
оригинальный проект), переезд между хостингами без потери истории, отдельный remote для деплоя.
